    What the hub is doing:
    Numbers the panda shows:

    The bot reads the activity list the hub already keeps (which file, which tool, how many tokens). No model is asked, so it costs nothing while it plays. It stops drawing when the tab is hidden and stands still if Windows is set to reduce motion.

    Pass 2: what the scene tells you. The bamboo is the run's token allowance: it grows to the dashed outline, turns amber past the 80% notch and red at the cap. The tea cup is the cache: steam while warm, thinner as minutes pass, frosted when cold. The book cover and the screen carry the file name; the lamp board carries the command. Tests passed: green board and a cheer. Tests failed: the failing lamps blink red with the count. Stopped: the panda sits with a sign that gives the reason. Waiting for you: a bigger sign, rings on the floor, the line turns amber, and one soft chime if Sound is on (it is off until you press it). Gauges: from 60% a sweat drop and quicker hands, from 90% heavy eyelids and slow steps; at 97% the hub stops the run and the sign says so.

    How the master drives the areas

    • Records apply at once, with Undo. The master writes a line the hub understands (RECORD: asset add …, RECORD: asset stage …). The hub checks it against a fixed form, writes the asset register, logs the change, and shows a chip with Undo in the chat and in Assets. Only Wanted, Received and Staged can be set this way.
    • Everything else is a button you press. Approve, Start, Resume, Close exist today. New: run tests, release, check, index, commit, dev server, restart. The master proposes; nothing happens until your press.
    • The master stays read-only. It never edits files or runs commands itself. File edits go through a run from an approved plan (or the Quick fix, D3).
    • The master sees more. Each message already starts with a status block. v2 adds: files changed since the last commit, the last test result, asset counts by stage, and what is new in assets-src.

    The cache strip

    • Where: at the top of the chat and of each run's page.
    • What it shows: how big the conversation is, whether the cache is warm, and how the last message split into re-used tokens and newly written ones.
    • Where the numbers come from: the usage figures every reply already carries. The hub saves them with the time of the reply. No model call.
    • The countdown is not shown yet. The real cache lifetime on this PC is unverified. The hub will learn it from normal use: for every message it notes the gap since the last one and whether the cache was re-used. Until it has seen a clear limit it shows "last reply N minutes ago".
    • Warnings before a costly action: switching model (the whole conversation is written again) and sending after a long break. Each offers the cheaper way, usually a new chat.
    • To confirm in the build: the "of 200k" size comes from a field in the reply's summary; if it is absent the bar shows the count alone.

    Commit

    • You tell the master "commit", or open Commit at the bottom of the tree. Asking the master costs one chat message (about 5k to 10k tokens) because it writes the message. Opening Commit yourself costs nothing: the hub suggests a message from the titles of the finished steps.
    • One batch: every changed file since the last commit, minus assets-src/, .claude/, .hub/, .dev.vars, simproject.code-workspace. Those five can never be ticked.
    • Warnings, not blocks: tests not passed since the last change, a file over 5 MB, files written by a run that did not finish (unticked by default). No proposal while a run is working.
    • The press runs a script with GitHub Desktop's git: add exactly the listed files, commit with the message. Never "add everything", never amend, never push, never force. If files changed after the list was shown, the hub refuses and shows the new list.

    Scene editor E5 still fits

    E5 can run as it is written. Its "Scene edit" item lands under Scene editor in the Work tree, as in the mock. Three things change around it, none needs a new E5 revision:

    • E5 says "the hub never commits". That stays true for E5's own routes; committing arrives separately in V3.
    • E5 builds its own Check (release, then tests). V2 moves that into Tools so there is one Check, whichever step is built first.
    • E5's Scene page must follow the layout rule: cards no wider than the dashed line. V1 applies it to all pages, the Scene page included.
